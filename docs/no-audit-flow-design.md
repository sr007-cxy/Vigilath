# 工作台流程重构设计(去审核版)

> 背景:产品决定去掉「用户提交审核 / admin 审核」这一步。admin 直接为客户在工作台建项目并跑分;客户在自己的看板里看结果。本文聚焦**工作台菜单结构、各页面展示、admin 操作动线**。

---

## 1. 角色与边界

| 角色 | 入口 | 能做什么 |
|---|---|---|
| **admin** | `/workbench/*` | 代客户建项目、改画像、起跑、看进度、复审文案、标记投放 |
| **客户** | `/dashboard`、`/brand-growth/*` | 只读看健康报告、看已发布内容 |

客户不再自己建项目、不再提交审核。所有项目均由 admin 在工作台代建。

---

## 2. 新流程总览

```
admin 建项目
  │
  ▼
填画像 → 选种子词 → 扩 query → admin 自己看一眼
  │
  ▼ ┌──────────────────────────────────────────┐
点「启动项目」└→ 一个按钮串起下面 4 件事       │
                                                │
   1. 调 /run-topic 跑分 → 拿 run_id            │
   2. 写 ExecutionPlan 行(快照 + run_id)      │
   3. 异步:LLM 生成文案稿                       │
   4. 异步:邮件通知客户「项目已启动」           │
  ─────────────────────────────────────────────┘
  │
  ▼
admin 进「执行计划书」页 → 看 run 进度 / 快照 / 文案状态
  │
  ▼
admin 进「文案复审」→ 通过 / 退回 / 标记投放
  │
  ▼
客户在 dashboard 看健康报告 + 已发布内容
```

### 4.4 项目详情:stepper-tabs 导航(**关键**)

#### 4.4.1 整体形态

进入某个项目后(URL 含 `topicId`),所有项目相关页面共享一个 layout,顶部固定一条 **stepper 式 tabs**——既是状态条又是导航 tab:

```
┌─────────────────────────────────────────────────────────────────────┐
│ ← Acme Inc. / XX 公司 GEO 监测              [🩺战略方案] [⚙跑分历史]│
│ ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━│
│                                                                     │
│   ①─────②─────③─────④─────⑤                                   │
│   ✓     ✓     ✓     ⋯     ─                                       │
│  画像   种子   计划书 文案   投放                                   │
│  必填齐 5 条  跑分中 3/5    0/3                                     │
│                                                                     │
│ ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━│
│   (当前 step 对应内容,见下面 4.4.2 - 4.4.6)                     │
└─────────────────────────────────────────────────────────────────────┘
```

**Stepper 状态符号**:

| 符号 | 含义 | 颜色 |
|---|---|---|
| `✓` | 完成 | 绿 |
| `⋯` | 进行中 / 部分完成 | 黄 |
| `─` | 未开始 | 灰 |
| `✗` | 失败(如 run failed) | 红 |

**点击行为**:每步都可点跳路由;前置 step 没完成的也允许点(admin 是熟手,不强制顺序)。

#### 4.4.2 五步 step 与路由对应

| Step | 标题 | 路由 | 完成判定 | 默认跳哪 |
|---|---|---|---|---|
| ① | 画像 | `/workbench/topics/:id/profile` | 画像必填字段齐 | TopicEditor 的画像 tab |
| ② | 种子监测 | `/workbench/topics/:id/queries` | ≥1 个 selected query | TopicEditor 的种子/query tab |
| ③ | 计划书 | `/workbench/topics/:id/execution-plan` | `ExecutionPlan.status=ready` | 现 ExecutionPlan.tsx(不动) |
| ④ | 文案 | `/workbench/topics/:id/docs` | 全部 doc.status ∈ {approved, published, rejected} | 项目内文案列表(本项目过滤) |
| ⑤ | 投放 | `/workbench/topics/:id/published` | 全部 approved doc 都已 published | 已投放清单 + 标记投放面板 |

辅助页(放右上角,不进 stepper):

- `🩺 战略方案 / 健康报告` → `/workbench/topics/:id/solution`
- `⚙ 跑分历史` → `/workbench/topics/:id/runs`

#### 4.4.3 Step ③ 计划书页(原 §4.4 ExecutionPlan)

骨架不变(Overview / Progress / PublishingPlan / Changelog / Expansion 五块),改两处:

- 去掉原页面的 header(因为 stepper-tabs 已经接管标题区),只渲染 5 个 section
- 「重新启动」按钮挪到 stepper 右上角(整个项目层级,不属于单 step)

```
┌─ Step ③ 计划书 ──────────────────────────────────────────┐
│ ▼ 项目总体状况(Overview)                                │
│ ▼ 运行进度(Progress)  ━━━━━━━○━━━━ 12/15 (80%)        │
│ ▼ 发文计划(PublishingPlan)                              │
│ ▼ 主题日志(Changelog)                                   │
│ ▼ 泛化日志(Expansion)                                   │
└──────────────────────────────────────────────────────────┘
```

#### 4.4.4 Step ④ 文案 / Step ⑤ 投放

这两步是「同一批 doc 的不同生命周期」,所以拆成两步:

- Step ④ 文案:focus `draft / pending_review / approved / rejected`,目标是「都过审」
- Step ⑤ 投放:focus `approved / published`,目标是「都投出去」

项目内的文案视图等于「文案复审页(`/workbench/content-review`)预过滤本项目」,UI 完全一致;只是入口不同。

#### 4.4.5 状态条 chip 与 stepper 的关系

卡片上的 chip 行 = stepper 的折叠态(只显示进度,不显示数字 step)。两者数据源同一套(`_pipeline_state(topic)` 函数,新写,替换原 `_diagnose_state / _plan_state / _content_state` 拼装)。

## 5. 后端 API 改动

### 5.1 新增

`POST /admin/topics/{topic_id}/start` —— 启动项目

前置校验:画像必填齐 + ≥1 个 selected query + ≥1 engine。

副作用(`_post_approval_pipeline(topic_id, admin_id)`,从 `approve_topic` 抽出来):

1. `_trigger_run_topic_sync(topic_id)` → `run_id`
2. `_build_execution_plan_snapshot(t, run_id)` → 写 `AiTelemetryTopicExecutionPlan`
3. `background.add_task(_schedule_content_generation, topic_id, plan_id)`
4. `background.add_task(_send_project_started_email, ...)`

幂等:同 topic 已有 `ready / generating` plan → 返回最新一条,不重复触发。前端「重新启动」按钮带 `force=true` 才允许再跑。

### 5.2 修改

`POST /admin/users/{user_id}/topics`(`ai_telemetry.py:472`)
- 保持「落库即 approved」,**不再自动**触发跑分
- 返回后前端引导 admin 点「启动」

### 5.3 删除

- `POST /admin/review/topic/{id}/approve`、`/reject`
- `POST /admin/review/seed/{id}/{idx}/approve`、`/reject`
- `POST /admin/review/queries/{id}/approve`、`/reject`
- `POST /topics/{id}/submit-for-review`

### 5.4 状态字段瘦身

`submission_status` 字段保留(避免 schema 抖动),但枚举从 `draft / pending / approved / rejected` 收敛为 `draft / approved`,不再读 `pending / rejected` 分支。
