# 浏览器自动化(browser-service)限制与扩容方案

> 背景:AI 遥测跑批要把"一组问题 × 一组 AI 引擎"打到各引擎拿真实答案。随着监测问题从百级涨到万级、百万级,browser 抓取的引擎成为瓶颈。本文梳理限制、解法,并给出按天的 IP / 账号容量测算。
>
> 适用引擎:国内五大(deepseek / 豆包 / 通义千问 / 文心 / 元宝)。

---

## 一、引擎分通道:谁能走 API,谁只能走浏览器

GEO 要测的是**用户在网页版搜出来看到的、带联网搜索的答案**,不是裸模型答案。所以能不能 API 化,取决于"该引擎的 API 有没有联网搜索"。

| 引擎 | 官方 API | API 是否带联网 | 结论 |
|---|---|---|---|
| 豆包 | ARK Bot | ✅ 有(已在用) | **走 API** |
| 通义千问 | DashScope | ✅ `enable_search=true` | **走 API** |
| 文心 | 百度千帆 | ✅ 搜索插件 | **走 API** |
| **deepseek** | 有 | ❌ **API 无联网模式** | **只能 browser** |
| **元宝** | ❌ **无 API** | — | **只能 browser** |

**关键结论**:豆包 / 通义 / 文心 可 API 化,量再大也只是并发 + 预算问题;**deepseek 和元宝两个只能走浏览器**,是扩容的真正瓶颈,需专门解决。

---

## 二、浏览器自动化的限制

1. **deepseek 按出口 IP 风控**:单个出口 IP 短时间跑 ~38 条就被封,封后该 IP 上**所有账号一起失败**(换号无效)。实测 2026-06-01:一次性 143 条 burst,38 条后 IP 被封,后续 105 条全挂。
2. **元宝按账号限**:~27 条/账号/天(经验值);IP 不敏感(与通义/文心同出口 IP 跑批正常)。
3. **机器数 ≠ IP 数**:同一机房多台 VM 常共用一个 NAT 出口。实测 vm01/vm03 共用 `123.125.194.110`,vm02 是 `123.125.194.109` → 3 台只有 2 个出口 IP。**加机器加不出新 IP**,只有代理能加 IP。
4. **速率敏感**:burst(高速率)必封;drip 慢速(~2 条/小时)安全。
5. **hot session 单账号串行**:一个 worker 一个引擎只绑一个账号、内部串行;并发需多 instance。
6. **登录态会失效**:session 过期 / 验证码隔离;需持续续期。

> deepseek 缺的是 **IP**,元宝缺的是**账号** —— 两者杠杆不同。

---

## 三、解决方案

已上线(`engine_session.py` / `runner.py` / `scheduler.py`,2026-06-01):
- **三层换号**:失败即换 + 每 N 条定期轮换 + **IP 熔断**(连续换号仍失败就停手,不把账号全喂进黑名单)。
- **per-engine 路由**:`BROWSER_SERVICE_<ENGINE>` 把单个引擎指到不同出口 IP 的 worker(deepseek 已可单独切到干净 IP)。
- **drip 限速**:每引擎日上限 + 摊到 24 小时(7 天周期),避免 burst。

要支撑万级 / 百万级还需:
1. **代理池(给 deepseek 加出口 IP)**:接商业轮换代理(住宅 / 移动 IP),browser per-context 走代理。**唯一能把 IP 从个位数扩到成百上千的办法。**
2. **账号 farm(给元宝加账号)**:批量注册 + 持续续期,health 监控(engine_sessions 池已具备)。
3. **身份绑定(防风控)**:每个"身份" = 账号 ↔ 固定代理 IP ↔ 固定指纹,**整体轮换**,不单独换 IP 或单独换号。
4. **worker 集群**:browser-service 容器化,每 worker 绑一个身份,自动扩缩。
5. **抽样**:量极大时 deepseek / 元宝**抽样**实测,统计外推可见度(可见度是统计指标,不必穷举)。

---

## 四、按天容量测算

前提(基于实测 / 经验,可再校准):
- deepseek:**~35 条/IP/天**;账号按 IP 约 1:1 配 + 备用。
- 元宝:**~27 条/账号/天**;每 IP 可挂多账号(≤~20)。
- 豆包/通义/文心:走联网 API,不吃 browser IP/账号,只要几把 key。
- 口径:每个问题问 5 个引擎 → **每引擎日量 = 问题数**。

### 单引擎需求

| 引擎 | 通道 | 10,000/天 | 50,000/天 | 100,000/天 |
|---|---|---|---|---|
| **deepseek** | browser(缺 IP) | ~290 IP / ~400 账号 | ~1,430 IP / ~2,000 账号 | ~2,860 IP / ~4,000 账号 |
| **元宝** | browser(缺账号) | ~370 账号 / ~20 IP | ~1,850 账号 / ~95 IP | ~3,700 账号 / ~190 IP |
| 豆包 | ARK API | ~2-3 key | ~2-3 key | 靠并发 + 预算 |
| 通义 | DashScope API | ~2-3 key | ~2-3 key | 靠并发 + 预算 |
| 文心 | 千帆 API | ~2-3 key | ~2-3 key | 靠并发 + 预算 |

### browser 部分合计(deepseek + 元宝)

| | 10K/天 | 50K/天 | 100K/天 |
|---|---|---|---|
| **出口 IP** | ~310 | ~1,500 | ~3,050 |
| **账号** | ~770 | ~3,850 | ~7,700 |

---

## 五、结论与建议

- **豆包 / 通义 / 文心**:接官方联网 API,IP/账号需求≈0,百万级靠并发 + 预算解决。
- **deepseek / 元宝**:只能 browser,穷举到 10 万/天就要 ~3,000 IP + ~7,700 账号(商业代理池 + 账号 farm 规模),**不经济、不稳定**。
- **推荐路线**:
  1. 豆包/通义/文心 → **API 全量**;
  2. deepseek/元宝 → **抽样 browser + 代理池(deepseek)+ 账号 farm(元宝)+ 身份绑定**;抽样把 IP/账号需求压到几十 IP + 几百账号即可覆盖。
- **第一步落地**:给 browser-service 接入**代理池(per-context 代理 + 身份绑定)**——这是 deepseek 扩容的根;元宝侧同步补账号池。
